# 分支与发布

## 分支职责

| 类型 | 命名 | 用途 |
| --- | --- | --- |
| 稳定主线 | `main` | 已验证、可复现的比赛入口；目前仍以基线代码为主 |
| 功能或性能 | `feat/<domain>/<slug>`、`perf/<domain>/<slug>` | 单一功能或优化，完成后审查集成 |
| 诊断或基准 | `probe/ev/<slug>`、`bench/ev/<slug>` | 观测与比较，不默认进入正式运行路径 |
| 文档或仓库整理 | `docs/<slug>`、`refactor/<slug>` | 与行为变更分开提交 |

`domain` 使用 `dp`（Data Pipeline）、`ck`（Compute Kernel）、`qs`（Query Scheduling）、`sa`（Search Algorithm）或 `ev`（Evaluation）。任务号如 `DP-01` 是文档和实验中的稳定索引；分支名用功能名称说明内容，不把任务号、方案号与实验轮次重复编码。方案可使用 `DP-01/V02-direct-map` 这样的稳定标识，实际继承由 Git 提交图和实验元数据确定。

通常从最新 `main` 创建短期分支。确需在另一方案上累积开发时，明确记录父分支的提交 SHA。领域集成分支只在确有联合验证需求时临时建立，并注明参与分支和验收日志；不预建常驻 `integration/*`。正式发布用指向已验收提交的 tag，并在发布记录中说明对应完整运行日志和环境。未经验证的实验提交不标记为正式版本。

## 集成检查

1. 审查变更范围和真实祖先，避免把历史实验链整体带入主线。必要时提取独立提交或最小代码差异。
2. 验证脚本语法、构建、冒烟测试、命中表与 MSA 一致性，以及正式 100-query ROC10 约束。无法运行的项目明确记为 `SKIP`。
3. 记录 `prologue + search` 总用时和多轮比较，再决定是否将性能方案集成。不得把单次时间改善当作结论。
4. 合并后核对远端引用和正式入口。保留旧分支，直到实验引用、协作者和可恢复备份均已核实。

当前旧分支的快照、继承关系与迁移状态见 [迁移索引](MIGRATION.md)。
