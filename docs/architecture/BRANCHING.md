# 分支与发布

## 分支职责

| 类型 | 命名 | 用途 |
| --- | --- | --- |
| 稳定主线 | `main` | 已验证、可复现的比赛入口；目前仍以基线代码为主 |
| 功能、修复或性能 | `feat/<task-id>/<slug>`、`fix/<task-id>/<slug>`、`perf/<task-id>/<slug>` | 一个任务的一项可审查改动，完成后验证和集成 |
| 诊断或基准 | `probe/<task-id>/<slug>`、`bench/<task-id>/<slug>` | 观测与比较，不默认进入正式运行路径 |
| 文档或仓库整理 | `docs/<slug>`、`refactor/<slug>` | 与行为变更分开提交 |
| 历史存档 | `archive/<task-id>/<slug>` | 保留已被新候选取代的实验提交，不作为当前集成入口 |

`wip/<slug>` 只用于本地保存尚未拆分的混合工作树，不推送、不发 PR；拆分后各项工作仍须进入带任务号的分支。服务器原有未提交改动属于这种状态，不能仅因旧分支名把它视作已完成的 QS-01 实现。

`task-id` 采用小写 `dp-01`、`ck-01`、`qs-01`、`sa-01` 或 `ev-01` 等形式，与文档及实验目录中的大写 `DP-01` 等编号一一对应。`slug` 用小写英文和连字符说明具体改动，例如 `perf/dp-01/direct-map`、`feat/qs-01/query-parallel-scheduler`。一个任务可有多个方案分支；同一方案的多轮测试共用代码分支，运行编号只出现在实验目录和元数据中。方案标识如 `DP-01/V02-direct-map` 也不强制写进分支名。

一个分支涉及多个任务时，按主要行为选一个任务号，其他任务在 PR 和实验索引中交叉引用。跨任务的纯文档或目录整理可使用不带任务号的 `docs/`、`refactor/`。重命名、存档或删除历史引用前记录原名、目标名及完整提交 SHA；旧分支名不代表已通过正确性或性能验收。

PR 的 `Branch name` 工作流检查分支格式；格式通过不代表代码、实验或性能验收。新建 PR 前先核对任务号、方案名和 Git 真实祖先。

通常从最新 `main` 创建短期分支。确需在另一方案上累积开发时，明确记录父分支的提交 SHA。领域集成分支只在确有联合验证需求时临时建立，并注明参与分支和验收日志；不预建常驻 `integration/*`。正式发布用指向已验收提交的 tag，并在发布记录中说明对应完整运行日志和环境。未经验证的实验提交不标记为正式版本。

## 集成检查

1. 审查变更范围和真实祖先，避免把历史实验链整体带入主线。必要时提取独立提交或最小代码差异。
2. 验证脚本语法、构建、冒烟测试、命中表与 MSA 一致性，以及正式 100-query ROC10 约束。无法运行的项目明确记为 `SKIP`。
3. 记录 `prologue + search` 总用时和多轮比较，再决定是否将性能方案集成。不得把单次时间改善当作结论。
4. 合并后核对远端引用和正式入口。迁移分支前记录原 HEAD，确认新引用及关联 PR 可用后再删除旧引用；原始实验记录不随分支清理而删除。

旧分支到规范名称的逐项映射、继承关系与迁移状态见 [迁移索引](MIGRATION.md)。
